# Traps

Every row cost real time or real money on a live pod. Dates are when it was hit.
Most rows are enforced by an assertion in `tests/test_runpod_ops.py`; search that file
for a row's keyword to find its tripwire. **Add the assertion before you add the row.**

Read the whole table once before your first pod. Skim it again whenever something
"looks like" a hardware fault, a bad workflow, or a hung boot: it is usually here.

| trap | rule |
|---|---|
| **STOP/START DISCARDS THE CONTAINER DISK — only `/workspace` survives.** Downloaded models are intact after a resume, but EVERY `pip install` and `apt` package is gone (they live in container site-packages, not the volume). The pod looks healthy — models present — then ComfyUI will not start. (2026-07-26) | after ANY resume, re-run the dependency half of `provision-comfyui.sh` (it is idempotent and skips the model downloads). Budget ~3-4 min, not a full re-provision. |
| **POD STORAGE IS SCRATCH — SYNC OUTPUTS AS THEY LAND.** A long batch wrote frames to pod-local disk with no copy-back; RunPod stopped the pod (balance), the GPUs were reclaimed, restart failed, and ~200-400 rendered frames + ~$22 were lost outright (2026-07-26). | run `local/sync-outputs.sh <host> <port> <remote_dir> <local_dir>` alongside EVERY batch. If an artifact is not on the laptop, it does not exist. |
| **Match the GPU to the requirement, not to the ceiling.** fp8 needs cc>=8.9 — that is **Ada** (L40S $0.99, RTX 6000 Ada $0.84), not only Hopper (H100 $2.99). Reaching for H100 x2 cost ~6x for the same capability and drained the account mid-run. | pick the CHEAPEST tier that satisfies the constraint; `--max-hours` is a budget ceiling, use it |
| **STOPPING CAN STRAND THE POD.** Stop releases the GPU; restart fails with *"not enough free GPUs on the host machine"* and pod-local models are then unreachable (they cannot migrate). Stock is per-**HOST**, not per-DC — "High stock A40" did NOT save us (2026-07-25, cost a full re-provision). | Do **not** auto-stop a pod whose models live on pod-local disk unless you accept re-provisioning. During an active session set `--idle-min` high (90+) **and** hold `/workspace/.busy`. Auto-stop is for *forgotten* pods, not for pausing between steps. |
| **torch 2.4 is too old for Qwen-Image-Edit** — `scaled_dot_product_attention() got an unexpected keyword argument 'enable_gqa'` (that arg arrived in torch 2.5). The stock `runpod/pytorch:2.4.0-cuda12.4` image hits it. | install the torch trio **before** generating, not after |
| **UPGRADE torch/torchvision/torchaudio TOGETHER OR COMFYUI WON'T BOOT.** Bumping torch alone leaves torchaudio built against the old ABI; ComfyUI imports torchaudio at startup and dies with `libtorchaudio.so: undefined symbol: _ZN2at4_ops9fft_irfft4call…`. pip prints only a yellow *"torchaudio 2.4.1 requires torch==2.4.1, but you have 2.6.0"* — **that warning is FATAL, not cosmetic** (2026-07-25, cost a restart cycle). | one command: `pip install torch==2.6.0 torchvision==0.21.0 torchaudio==2.6.0 --index-url https://download.pytorch.org/whl/cu124`, then verify all three import before launching |
| **All-in-one checkpoints vs bare UNETs.** `flux1-dev-fp8.safetensors` (Comfy-Org/flux1-dev, repo ROOT) bundles model+CLIP+VAE → `CheckpointLoaderSimple`, whose outputs are **MODEL=0, CLIP=1, VAE=2** from ONE node. Kontext/Qwen ship bare UNETs → `UNETLoader` + separate CLIP/VAE. | never wire three loader nodes each read at index 0 — it silently hands back MODEL everywhere |
| **HF paths shift.** `flux1-dev-fp8` and `flux1-redux-dev` are at the repo **root**, not under `split_files/` — guessing cost a re-download. | verify with `https://huggingface.co/api/models/<repo>` before writing a provision script |
| **The RunPod HTTP proxy chokes on bulk payloads** (`/object_info` is multi-MB and times out). | use the proxy/tunnel for control + small calls; run batch harnesses **ON the pod** against `localhost:8188` and ship back only results |
| **A missing model file fails LATE and CRYPTICALLY.** A silent `MISS` surfaced 20 min later as `shape '[1,16,48,2,84,2]'` in KSampler (Z-Image, wrong VAE) and as an apparent bad-HF-path (FLUX.2 35GB staged to a too-small /tmp). | `mkdir -p` the DEST as well as the stage; make MISS loud; list models on disk and fail before any workflow runs |
| **Model FILENAME COLLISIONS across families.** Z-Image and FLUX both ship a file named `ae.safetensors` — ComfyUI loads whichever it finds and dies deep in the sampler. | rename per family on download (`z_image_ae.safetensors`); provision now warns on duplicate basenames |
| **One long-lived ComfyUI accumulates RAM across big model loads and gets SIGKILLed by the container cgroup.** Signature: log stops mid-load, NO traceback, no python process, GPU at 0 MiB. Looks like a workflow bug; it is container RAM. | restart ComfyUI between models — one model per process for multi-model benchmarks |
| **Z-Image vs FLUX.2-Klein share the `qwen_3_4b` encoder**; ONLY the CLIPLoader `type` distinguishes them (`flux2` -> Klein, anything else -> Z-Image, `comfy/sd.py`). | a wrong `type` silently loads the wrong model family |
| **SSH port REMAPS on stop/start** (IP often stays; 22132→22016, and 17315→19618→12358 on 2026-11-20) | never reuse a pre-pause port — `pod_ctl.py conn <podId>` every time |
| **Right after a start, v2 serves the PREVIOUS run's SSH address.** 2026-11-20: status RUNNING, `ssh.direct` and `runtime.ports` both still showed the pre-stop port, with `runtime.uptime` 582 s while `startedAt` was 11 s old. A stopped (EXITED) pod also kept its old `ssh.direct`, and both fields blinked out for single polls while running | `conn` takes the port-22 mapping from `runtime.ports` only when status is RUNNING and the uptime fits since `startedAt`; anything else prints not ready, so poll |
| **Network volumes DC-LOCK the pod** | use pod-local `--volume-gb`. a volume created in US-WA-1 was **stranded** when that DC hit zero GPU stock: it could not be attached at all |
| RunPod **SSH proxy** is PTY-only | use **direct-TCP SSH** — only it supports non-interactive commands, `scp`, and `-L` |
| background job dies on SSH close | `nohup setsid <cmd> > <log> 2>&1 </dev/null & disown` |
| **`ssh pod '<launch>; echo ok'` hangs until the job ends.** Timed live 2026-11-20: 3 s with the job's output redirected, 28 s (the job's whole life) without it. A backgrounded job that keeps the ssh channel's stdout holds the connection open, so an agent's call blocks and looks hung | Every launch redirects all three streams: `> log 2>&1 </dev/null & disown`. A tripwire checks every launch line we ship, prose included |
| **container RAM (~55GB cgroup), not VRAM**, causes the OOM | keep models GPU-resident (`offload_percent=0`, `force_offload=false`) |
| stopping releases the GPU | pause only on **High-stock** GPUs, or you may not get it back |
| **AUDIO/TTS nodes need `ffmpeg` + apt libs the image lacks.** RVC shells out to `ffmpeg` and catches the failure **per file**, then reports *"RVC dataset prep produced no usable voiced training entries. F0 extraction likely failed; check the selected pitch method and RMVPE model availability"* — blaming F0/rmvpe when the real cause is a missing binary. Cost ~1h chasing rmvpe.pt, torch's `weights_only` flip, and a suspected filename-stem mismatch (2026-07-26). | `apt-get install -y ffmpeg libsamplerate0-dev portaudio19-dev` **before** any audio node. When an error names a subsystem, verify that subsystem is actually reached — run a CONTROL on different input to see if the failure is data-specific |
| **Node REGISTERED ≠ engine INSTALLED.** TTS-Audio-Suite registers node classes even when an engine's bundled impl is absent: it appears in `/object_info`, counts toward node totals, then raises `ImportError` at execute. I counted "72 audio nodes" and called the install a success. | trust `install.py`'s *EXTERNAL ENGINE RUNTIME CHECKS* AVAILABLE list, not the node count |
| **`/workspace` is MooseFS (network) storage.** ComfyUI blocks in `WCHAN request_wait_answer` importing ~2000 files and sits at *"Using pytorch attention"* for minutes looking hung. A recursive `grep`/`find` over the tree will time out the SSH session. | be patient on boot (90x5s readiness loop); run searches **detached to a file** on the pod, then `cat` the file |
| **Block-buffered stdout makes a live job look dead.** A redirected `python foo.py > log` showed an empty log for 8 minutes; the job was fine. Worse, ComfyUI queues **server-side**, so killing the poller does not stop the work — I re-queued duplicates. | always `python3 -u`; watch the OUTPUT DIRECTORY or `/history`, never the poller |
| **A ComfyUI graph with no terminal OUTPUT node is rejected** (`prompt_no_outputs`) — so a prep/analysis node cannot be tested in isolation. | chain to `SaveAudio`/`SaveImage` and smoke-test at minimum work (`epochs=1`) instead |
| `cmd \| head` hides the real exit code / truncates errors | keep full logs; a truncated log once hid a fal 403 balance error for a whole batch |
| **A sync sentinel that does not name WHAT it covers vouches for everything.** `/workspace/.synced` was global, so any running loop asserted all outputs were safe — and the terminate-rather-than-strand branch trusts exactly that signal, so it could have destroyed a pod still holding unsynced frames from another directory (2026-07-27). Separately, 26 sync loops were left retrying a DEAD host for ~21h: a loop with no lifecycle outlives the thing it syncs. | sentinels are per-directory (`/workspace/.synced.d/<slug>`); run autostop with `--outputs-root` so EVERY dir with recent output needs its own fresh sentinel, and a sentinel older than the newest file re-flags it. Without it the check logs `[WEAK]`. Kill sync loops when their host dies |
| **`/workspace/.busy` IS A HEARTBEAT, NOT A FLAG.** A sweep script touched it at the top and exited without removing it; the watchdog dutifully "held" a completely idle H100 for **3 hours (~$9)**. A lock that outlives its job is indistinguishable from one nobody cleaned up (2026-07-27). | `autostop.py --lock-ttl-min` (default 20) IGNORES a stale lock. Long jobs must REFRESH it: `bash hold-busy.sh -- <cmd>` (traps EXIT/INT/TERM so it always releases). Never `touch .busy` and trust it |
| **A `pkill -f` pattern silently stops matching when you add a flag.** A launcher used `pkill -f 'main.py --listen'`; adding `--disable-cuda-malloc` *before* `--listen` broke the match, so the next relaunch would have started a second pair of instances on top of the live ones. Same class of bug: `pgrep -af 'main.py'` also matches your own `bash -c` wrapper (2026-07-26). | **Verify the pattern with `pgrep -af` before trusting the `pkill`** — it must list exactly the pids you mean. Match on a regex that survives flag changes (`'main\.py.*--listen'`) |
| **Backgrounded jobs are not visible to `pgrep` the instant you launch them.** A launcher's `while pgrep -f gen-refflash2.py; do sleep 30; done` completion loop found nothing one second after a `setsid … disown` launch, printed `FULL_RUN_DONE`, and **deleted `/workspace/.busy` while 554 frames were still queued** — handing the pod to the idle watchdog. | `sleep 90` before any "wait until my children exit" loop, and re-`touch /workspace/.busy` after any launcher exits early |
| **`uptime` inside the container reports the SHARED HOST's load, not yours.** A load average of 35–60 looked like CPU saturation and sent me chasing a contention theory; the host has **256 cores**, our cgroup allowed **54.4** (`/sys/fs/cgroup/cpu.max` = `5440000 100000`) and our processes were using ~24 (2026-07-26). | measure YOUR usage: `ps -eo pid,pcpu,comm --sort=-pcpu` against `cat /sys/fs/cgroup/cpu.max`, never `uptime`. Same trap as `free`/`nproc` in a container |
| **A stale server-side queue masquerades as a hardware fault.** After a relaunch at lower resolution, GPU0 showed **23.8 s/it and 840 MHz** against GPU1's 7.8 s/it and 1440 MHz — I nearly filed it as a throttled card. It was the OLD 4.2 MP prompts still draining: killing the harness never cancelled them. Once cleared, both cards sat at 1335/1455 MHz and matching s/it (2026-07-26). | before blaming hardware, check `/queue` for work you thought you killed. Clocks and power *follow* the workload — a heavier queued job is not a slower GPU |
| **MEASURE BEFORE YOU PROJECT — estimates were wrong 2-5x, twice in one session.** Quoted ~1.9h/$11; it ran 3.67h/$22 **and did not finish**. The per-frame figure had been measured warm, on ONE instance, ignoring two-instance contention and upload overhead. The very next projection was wrong again. | time the first 3-5 real frames under the ACTUAL final configuration, then project; set `--max-hours` as a genuine budget ceiling, not a formality |
| **RENDERING FAR ABOVE THE DELIVERY RESOLUTION — and lower is not automatically faster.** A 554-frame batch ran at 3136x1344 (**4.2 MP**) for frames on screen ~1/6 s, because FLUX.2 inherits size from the content-reference latent. Dropping to 1904x816 made it **SLOWER** (90 s/frame vs 70) — an odd token grid (119x51) appears to fall off the fast attention path. 1792x768 (112x48) plus no ref upscaling gave ~30% back. | set the output size deliberately instead of inheriting it, and prefer grid dimensions divisible by 16; **A/B it, do not assume smaller is faster** |
| **A `create` 400 MEANS NO CAPACITY, NOT BAD SYNTAX**: REST v2 answers 400 with only a human-readable detail. On REST v1 (retired 2026-11-15) it was a bare 500 (`Something went wrong`), and `create` wanted a **`gpuTypeId`** (`"NVIDIA GeForce RTX 4090"`) while `availability` printed a **`displayName`** (`"RTX 4090"`), so a capacity failure read exactly like a typo. On v2 both use the same id (checked 2026-11-20). | pass `--gpu` a comma list in COST order; `create` moves on at each 400. `availability` first, always |
| **THE GPU TABLE BELOW IS VIDEO-SHAPED — size to YOUR workload.** Its 48GB floor and 8xA40 recommendation exist for Wan 2.2 I2V. Voice/TTS is tiny: a single **24GB L4 @ $0.39/hr** ran Chatterbox/Bark/RVC/Moss comfortably. Following the table for an audio job overspends **~9x** (~$2 session vs ~$18). | read the table as "video defaults"; for audio/LLM/small-image work pick the cheapest card that fits the weights |
| **AN ACCOUNT-WIDE BALANCE STOPS *YOUR* POD** — `{"error":"start pod: Your account balance is too low to rent a pod...","status":500}`. A $0.39/hr pod became unstartable because a **concurrent session's** $5.98/hr B200 drained the account. There is no shared spend visibility between sessions; two pods at $0.39 and $1.98/hr were only discovered by listing. | `pod_ctl.py list` before assuming a start failure is about YOUR pod, and tell anyone (or any agent) sharing the account when you start an expensive pod; `pod_ctl.py balance` shows the burn rate |
| **A NODE PACK MAY SHIP ITS OWN ISOLATED PYTHON RUNTIME** — TTS-Audio-Suite runs engines in a subprocess against `runtimes/shared_legacy_t4/lib/python3.11/site-packages/`, so **the system torch you carefully pinned is irrelevant to it**. Hours went into repinning the system trio for an engine that never used it. | before fixing "its" torch, check whether the node ships `runtimes/` and inspect THAT env; a `Worker closed the response stream unexpectedly` from `execution.py` is a subprocess crash, usually VRAM |
| **MODERN POD IMAGES SHIP NO `setuptools`** — a legacy `setup.py` in a node's tree then dies at BUILD time with `ModuleNotFoundError: No module named 'pkg_resources'`, even though setuptools is listed later in the very requirements file pip never finishes. Chicken-and-egg. | `pip install setuptools` first; and when a node ships `install.py`, run it INSTEAD of `pip install -r requirements.txt` (TTS-Audio-Suite documents that a flat install does not work) |
| **`transformers` 5.x refuses `torch.load` on torch <2.6** (CVE-2025-32434) — which silently blocks any model shipping `.bin` rather than safetensors (Bark). The visible symptom is "model won't load", not a version error. | the cu121 wheel index tops out at torch **2.5.1**; if a node's installer falls back to cu121 you cannot reach 2.6 — repin from the **cu124** index |
| **`git clone` progress spam buries the real error** — ~4,000 `Updating files: 43% (429/991)` fragments hid a `ModuleNotFoundError` in the provisioning log. | `git clone --quiet` in any script whose log you intend to read |
| **`df` LIES ON A NETWORK VOLUME.** `/workspace` on MooseFS reports the shared pool (`756T … 83%`), not your allotment, so you cannot see that you are out of space until `OSError: [Errno 122] Disk quota exceeded` / `QUOTAERR 6` mid-download. A network volume **cannot be resized after creation** — the only fix is destroy + recreate + re-download. Described in-session as *"the single biggest time-sink"* (2026-07-18). | size the volume **≥100GB** at creation; never trust `df` on `/workspace`; track progress with `du -sh` on the destination |
| **The pod's HF CLI is `hf`, NOT `huggingface-cli`.** The old name is absent, so the line is a silent no-op — the script "succeeds", prints its done-marker, and downloads nothing (`du` showed 60K of an expected 40G). Compounded by model files living in **subfolders** and one upstream filename carrying a typo (`Wan2_1-InfiniTetalk-Single_fp16`). | use `hf download` with exact paths verified against `https://huggingface.co/api/models/<repo>`; **never** trust a done-marker |
| **A COMPLETION MARKER IS NOT COMPLETION.** `download.sh` printed `DL_ALL_DONE` on total failure because `set -e` does not catch a no-op command. The same class killed a batch: `POLLER_DONE downloaded=8 errors=3`. | monitor long jobs by **artifact size/count on disk**, never by the script's own success print. Make the check fail loudly on a MISS |
| **RunPod proxy status codes are diagnostic — and 502 is usually NOT a crash.** `404` = the port is not exposed (pod Edit -> Expose HTTP Ports). `502` = exposed but ComfyUI is down **or merely blocked** — its HTTP thread stalls during a heavy model load and recovers. Only `Connection refused` on `localhost:8188` **plus** an empty `pgrep` means it actually died. Cost real debugging time before it was pinned down. | read 502 as "busy or dead, check locally"; never restart a pod on a proxy 502 alone |
| **The proxy filters by User-Agent and gates writes.** Default `urllib` gets `HTTP 403: Forbidden` where `curl` on the same URL returns 200; POSTs from non-browser clients are refused outright. | set a browser UA for GETs; do writes over the SSH tunnel to `localhost:8188`, not through the proxy |
| **RunPod's APIs are Cloudflare-blocked for urllib's default User-Agent** — GraphQL since 2026-07-19, and **REST too since ~2026-10-19** (`pod_ctl list` died with `API GET /pods: error code: 1010`; the July note "REST is unaffected" had gone stale). (Both were the old APIs; see the next row.) | every `pod_ctl.py` request (REST and GraphQL) sends a **browser User-Agent**; a tripwire enforces it |
| **RunPod retired REST v1 on 2026-11-15.** `rest.runpod.io` stopped resolving, so every `pod_ctl` call and the watchdog's stop and terminate failed with `getaddrinfo failed`: a pod started by hand would have billed with nothing able to stop it. GraphQL still answers but is deprecated and retires in early 2027. v2 takes one GPU type per pod and reports no capacity as a plain 400. | both tools use REST v2 only (`https://api.runpod.io/v2`): `/pods`, `/pods/{id}/action`, `DELETE /pods/{id}`, `/catalog/gpus`, `/billing/balance`; `create` tries each `--gpu` in turn; a tripwire bans the v1 and GraphQL URLs |
| **A key piped from Windows Python ends in `\r`, and the watchdog could never act.** 2026-11-20: `sys.stdout.write(key + '\n')` on Windows sends CR LF, `read -r K` keeps the CR, and urllib refused every request with `Invalid header value`; the watchdog logged `stock=None` and `WILL NOT RETIRE` on every poll while the pod billed. That error text quotes the whole Authorization header, so the **key landed in the pod's log** (rotate a key that leaks this way). Same pipe as the 2026-11-15 run, whose watchdog was likely dead too | both tools `strip()` the key; the watchdog's `log()` scrubs `Bearer …` and the key from every line; tripwires for both. After starting the watchdog, read its log once it has polled: `gpu stock=None` means it cannot reach RunPod |
| **A Low-stock pod stranded within 10 s of a stop** (2026-11-20, RTX 2000 Ada, catalogue `LOW`): `start` answered *not enough free GPUs on the host machine* twice. The same test on a `HIGH`-stock 4090 stopped and started cleanly. Live confirmation of the stranding row above | the watchdog's rule holds: stop only on High stock, otherwise terminate once outputs are synced. Before a manual stop, check `availability` for the pod's GPU |
| **THE POD MAY LACK TOOLS YOU ASSUME EXIST** — depending on the image: no `curl`, no `tmux`/`screen`, no system `ffmpeg`. (The `runpod/pytorch:2.4.0` image used on 2026-10-23 *did* ship curl, so presence varies; never depend on it.) A readiness check written with `curl` fell through silently and launched the renderer before ComfyUI had bound its port, which then collided on 8188 and collected **0 clips from 20 that had actually rendered fine**. | probe (`command -v`) before depending on any binary; poll readiness with **Python**, not `curl` |
| **SSH keys are injected at pod BOOT from your ACCOUNT settings.** A key added after the pod started gives `Permission denied` forever. IP *and* port are reassigned on every Stop/Start; only the `<podid>-<uid>@ssh.runpod.io` proxy handle is stable. | put the key in RunPod -> Settings -> SSH Public Keys **before** creating, and re-read `pod_ctl.py conn` after every resume |
| **`uptime` is the right tool for the WRONG question — and vice versa.** Two lessons that look contradictory: it reports the SHARED HOST's load, so it is useless for "am I CPU-bound?" (measure `ps` against `/sys/fs/cgroup/cpu.max`) but it is exactly right for **"did I draw a saturated host?"** — a fresh pod showing load 28+ dropped SSH repeatedly and never ran. | check `uptime` **immediately after create** as a host-lottery test: if it is saturated, terminate and redraw. Read the load against `nproc`: the 28+ case was a small host, while a 256-core host at load 30-40 (2026-11-15) was about 15% busy and ran fine. Never use it to reason about your own process's CPU |
| **A VRAM squatter silently halves a multi-GPU render.** ComfyUI fixes "usable VRAM" from FREE VRAM at load time, once. A stale instance still holding ~22GB on GPU0 made the new one see 22.9GB and run FLUX.2 (33.8GB) **`loaded partially`** — 11.8GB streamed from CPU every step: **494 s/frame vs 127 s/frame on the identical card**. No error; `nvidia-smi` showed 100% util on both (2026-07-26). | `pkill -f 'main.py --listen'; sleep 8` **before** relaunching, then `bash check-gpu-load.sh <host> <port>` — it fails when any shard samples below 70% of the fastest (and on `loaded partially`, which only older ComfyUI prints). Never project throughput from the fast shard |
| **CURRENT COMFYUI NEEDS TORCH >= 2.7, AND PROVISION LIED ABOUT IT.** ComfyUI now pins `comfy-kitchen`, whose custom ops use `list[int]` annotations torch 2.6 rejects (`infer_schema ... unsupported type list[int]`), so ComfyUI died on import. Provision still printed `PROVISION_DONE`: its readiness loop used `curl` (absent on the image) and fell through. The watchdog counts "unreachable" as BUSY, so a dead 4090 idled ~75 min (2026-10-20). | the trio is now torch 2.14.0 / vision 0.29.1 / audio 2.11.0 (cu126), `comfy_kitchen` is import-checked, readiness is polled in Python, and a timeout prints `PROVISION_FAILED` + exits 1 — all tripwired. Grep the log for `PROVISION_FAILED`, not just `DONE` |
| **THE SYNC LOOP WAS FLAT AND STILL VOUCHED FOR THE OUTPUTS.** Results in per-run subdirectories: `ls` + `scp` (no `-r`) failed into `/dev/null`, it printed "pulled 4 new" and touched the per-dir sentinel the watchdog trusts — for GLBs that never left the pod (2026-10-20). Also: stopping the background shell task on Windows left the child `bash sync-outputs.sh` running. | `sync-outputs.sh` now lists recursively with sizes, streams via tar, checks `PIPESTATUS` and re-verifies every file before touching the sentinel. After stopping a loop, confirm with `Get-CimInstance Win32_Process` that no `sync-outputs` process remains |
| **COMFYUI CHANGED ITS LOAD LOG LINE.** 0.42.0's dynamic-VRAM loader logs `prepared for dynamic VRAM loading. 22700MB Staged`; `loaded completely` / `loaded partially` are gone. A health check keyed on the old text could never pass, and its message blamed CPU weight-streaming that was not happening (live 2xA40, 2026-10-23). | key health checks on **behaviour** (sampling speed parity across identical GPUs), not on log wording; `check-gpu-load.sh` now does |
| **THE WATCHDOG DECIDED RIGHT AND COULD NOT ACT — THEN EXITED.** On the first live run of this repo, `autostop.py` reached "idle 10 min → terminate" correctly, but its REST calls carried no browser User-Agent, so the stock check and the terminate both got Cloudflare **403**. The failure was logged, `retire_pod` reported success anyway, and `main()` returned: **the cost guard died and the pod kept billing** at $1.18/hr until terminated by hand (2026-10-23). | every RunPod call goes through one `_runpod()` helper with a browser UA; stop/terminate return real success; the watchdog **never exits while the pod may bill**, it retries every poll. All tripwired, and re-verified live: a fixed watchdog terminated an L4 pod by itself |
| **A SAFETY CHECK THAT CHECKS NOTHING READS AS A PASS.** `--outputs-root` only inspected *subdirectories*, and the example harness writes files straight into `/workspace/out`, so "outputs synced=True" meant "found nothing to check". Separately, `sync-outputs.sh` built its sentinel name with `echo … \| tr`, turning the trailing newline into `_` (`_workspace_out_`) while the watchdog looked for `_workspace_out`, so a real per-directory check could never have succeeded (2026-10-23). | the root itself counts when it holds files; both sides derive the slug identically (`printf`, trailing `/` stripped), and a test runs the script's own lines through bash and compares them with `autostop._slug()` |
